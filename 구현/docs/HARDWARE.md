# 하드웨어 구현 상세

**회로 부품은 보유분만으로 구성한다. 추가 구매 0개.**

단, **케이블은 별개다.** 보드가 Micro-USB이고 맥은 USB-C라 둘을 잇는 것이 필요하다.
- `USB-C ↔ Micro-USB` 케이블, 또는 `USB-A ↔ Micro-USB` + `A→C 젠더`
- ⚠️ **충전 전용 케이블은 데이터가 안 통한다.** 꽂아도 `/dev/cu.*` 에 포트가 안 늘면
  보드 고장이 아니라 케이블을 의심한다. 구형 안드로이드 충전 케이블에 흔하다

## 1. 부품과 핀 배치

| 역할 | 부품 | 인터페이스 | ESP32 핀 |
|---|---|---|---|
| 본체 | ESP32 DevKit (WROOM-32, 30핀) | — | — |
| 보행 측정 | MPU-6050 (GY-521) | I2C | SDA **GPIO21** · SCL **GPIO22** |
| 소리 출력 | 수동 부저 | PWM (LEDC) | **GPIO25** |
| 기록 화면 | 0.96" OLED (SSD1306) | I2C **같은 버스** | SDA 21 · SCL 22 |
| 수동 요청 | 택트스위치 | GPIO 입력 | **GPIO14** (내부 풀업) |
| 전원 | USB 보조배터리 | Micro-USB | — |

**I2C 두 장치를 한 버스에 붙인다.** MPU-6050은 주소 `0x68`, OLED는 `0x3C`라 충돌하지 않는다.
풀업 저항은 두 모듈에 이미 실려 있으므로 따로 달지 않는다. 버스 속도는 400 kHz.

**결선**
```
ESP32 3V3 ──┬── MPU-6050 VCC
            └── OLED VCC
ESP32 GND ──┬── MPU-6050 GND ── OLED GND ── 부저(−) ── 스위치 한쪽
GPIO21 ─────┴── MPU-6050 SDA ── OLED SDA
GPIO22 ──────── MPU-6050 SCL ── OLED SCL
GPIO25 ──────── 부저(+)
GPIO14 ──────── 스위치 다른쪽   (INPUT_PULLUP, 누르면 LOW)
```
※ MPU-6050의 `AD0`는 띄워 두면 `0x68`, 3.3 V에 붙이면 `0x69`가 된다. 띄워 둔다.
※ 부저를 GPIO에 직결하면 3.3 V라 소리가 작다. 더 키우려면 NPN 트랜지스터(2N2222) + 베이스 1 kΩ으로 구동한다.

## 2. 센서 설정

```
가속도 레인지   ±2 g          보행 가속도는 대부분 ±2 g 안에 들어온다. 분해능을 얻는다
DLPF           21 Hz         레지스터 0x1A = 4. 62.5 Hz의 나이퀴스트(31.25 Hz) 아래. 44 Hz로 두면 에일리어싱
샘플레이트      62.5 Hz       레지스터 0x19 = 15 → 1000/(1+15). ★ 64 Hz는 만들 수 없다 — 3절 참조
                             순서 주의: DLPF를 먼저 켜야 분주 기준이 1 kHz가 된다
자이로          사용하지 않음   보행 동결 판정에 필요 없다. 전류를 아낀다
```
**FIFO를 쓴다.** 센서가 내부 버퍼에 샘플을 모으게 하고 ESP32는 주기적으로 한 번에 읽는다.
매 샘플마다 깨어나 읽는 방식보다 I2C 트래픽과 전류가 모두 줄어든다.

## 3. 신호 처리 — 두 갈래로 나뉜다

같은 가속도 스트림에서 **걸음 검출**과 **동결 검출**이 병렬로 돌아간다.

```
MPU-6050 ─ 62.5 Hz ─ magnitude = √(ax² + ay² + az²) ─ 중력 성분 제거
                              │
              ┌───────────────┴───────────────┐
        [A] 걸음 검출                    [B] 동결 검출
        0.5~3 Hz 대역통과                256샘플 윈도우 · 75% 겹침
        피크 검출 (불응 250 ms)           Hanning 윈도우 → FFT
        최근 4걸음 간격 중앙값             3~8 Hz 파워 ÷ 0.5~3 Hz 파워
              │                                 │
        케이던스 (걸음/분)              Freeze Index → 임계값 + 유지시간
              └───────────────┬───────────────┘
                        동결 판정 시 → 케이던스로 템포 계산 → 부저 구동
```

### [A] 걸음 검출과 케이던스
- magnitude를 0.5~3 Hz 대역통과로 거른다. 걸음 성분만 남는다
- 피크를 찾되 한 걸음 뒤 **250 ms 불응 구간**을 둬서 같은 걸음을 두 번 세지 않는다
- 최근 4걸음의 간격에서 **중앙값**을 쓴다. 평균이 아니라 중앙값인 이유는 한 번 튄 값에 끌려가지 않기 위해서다
- 케이던스(걸음/분) = `60000 / 간격중앙값(ms)`

### [B] 동결 검출 — Freeze Index
- 윈도우 **256 샘플** = 기기(62.5 Hz)에서 **4.096초**, DAPHNet(64 Hz)에서 **정확히 4.000초**
  - 4초는 **Bächlin 2010(DAPHNet 논문)이 고른 값**이다. Moore 2008 원 논문의 윈도우 길이는
    확인하지 못했으므로 '원 정의와 같다'고 쓰면 안 된다
- **75% 겹침**(hop 64샘플)으로 **약 1초마다** 한 번 판정
- Hanning 윈도우를 곱한 뒤 FFT (`arduinoFFT` 라이브러리)
- 주파수 분해능 = fs / 256 → 62.5 Hz에서 **0.244 Hz**, 64 Hz에서 **0.25 Hz**
- 각 대역의 파워를 합산한다. **빈 번호를 상수로 박지 말고 실행 중에 fs에서 계산한다**
  - `bin = round(Hz × 256 ÷ fs)`, 구간은 `[lo, hi)` 반열림
  - 닫힌 구간으로 하면 3 Hz 빈이 분자와 분모에 **모두** 들어가 같은 값을 두 번 센다
  - 이렇게 두면 DAPHNet(64 Hz)에서 정한 임계값이 기기(62.5 Hz)로 그대로 넘어간다
  - 참고로 64 Hz·256점이면 보행 대역 = 빈 2~11, 떨림 대역 = 빈 12~31이다
- `Freeze Index = 떨림 대역 파워 ÷ 보행 대역 파워`
- **비율로 보는 이유**: 떨림의 절대 크기는 사람마다, 걷는 속도마다 다르다. 비율은 그 차이에 덜 흔들린다
- ⚠️ **FI 하나만으로는 '서 있기'와 '동결'이 구분되지 않는다.**
  가만히 서 있으면 분모(보행 대역)가 작아져 FI가 저절로 치솟는다. 연속 2회 조건으로도 못 막는다
  — 서 있는 내내 FI가 높게 유지되기 때문이다.
  → **판정식은 `FI ≥ 임계` 가 아니라 `FI ≥ 임계 AND 총파워 ≥ 하한`** 이다.
  Bächlin 2010이 Moore의 FI에 총 파워 임계를 덧붙인 이유가 이것이다
- 총 파워는 **창함수 보정을 거쳐 g² 단위로** 낸다. FI는 비율이라 Hanning이 분자·분모에서
  상쇄되지만, 절대값 문턱인 총파워 하한은 상쇄되지 않는다
- **임계값 하나로 확정하지 않는다.** 임계를 넘은 상태가 **2회 연속** 이어질 때만 동결로 본다.
  계단·방향 전환·물건을 집으려 멈추는 동작은 순간적으로 넘지만 이어지지 않는다
- ⚠️ **검출 지연은 구조적으로 3~4초다.** (`tests/`의 합성 신호로 측정한 값)
  ```
  hold=1 → 중앙값 2.8초      hold=2 → 중앙값 3.8초      hold=3 → 중앙값 4.8초
  ```
  4초짜리 창이 동결 구간에 충분히 들어가야 FI가 넘으므로, 유지 조건만 세면 안 된다.
  **'약 2초'는 창이 채워지는 시간을 빼먹은 숫자였다.**
  선행 연구의 261 ms는 구조가 다른 값이라 목표로 삼으면 안 된다. **줄이려 하지 말고 이 숫자를 보고한다**
- **유지 회수를 올리면 지연이 그만큼 늘어난다** — `유지 +1회 = 지연 + hop 1개(약 1초)`.
  오탐이 안 잡힐 때 유지를 3회로 올리는 건 흔한 처방이지만, 그러면 지연이 4.8초가 된다.
  **올렸으면 지연을 다시 재고, 검출 대상의 최소 지속시간 기준도 같이 올려야 한다**
- ⚠️ **하한이 두 개 있고, 서로 다른 것의 하한이다. 섞으면 성능을 잘못 읽는다**

  | | 값 | 무엇의 하한인가 |
  |---|---|---|
  | **평가 라벨의 하한** | 약 **2.0초** | `(윈도우/2) ÷ fs`. 이보다 짧은 동결은 '참값이 동결'인 윈도우를 못 만들어 **분모에서 통째로 빠진다** |
  | **검출의 하한** | 약 **3.8초** | 창이 채워지고 유지 조건까지 서는 시간(hold=2) |

  **그 사이 2~4초 구간이 함정이다** — 분모에는 들어가는데 구조상 거의 못 잡는다.
  그리고 이건 짧은 이벤트만의 문제가 아니다. **모든 이벤트가 앞쪽 두 윈도우를 놓치고**,
  그 고정 비용이 긴 이벤트에서만 희석된다. 합성 신호 측정값(hold=2, 임계 1.5):
  ```
  2.5초 → 40%    3초 → 48%    4초 → 61%    6초 → 75%    12초 → 87%
  ```
- ⚠️ **지표가 두 개이고 분모가 다르다. 짧은 이벤트에서 크게 갈린다**

  | 지표 | 세는 것 | 3초 이벤트 |
  |---|---|---|
  | **윈도우 단위** | 참값이 동결인 윈도우 중 몇 개를 맞췄나 | **48%** |
  | **이벤트 단위** | 이벤트 구간 **안에서** 한 번이라도 잡았나 | **0%** |

  차이의 원인 — **윈도우 단위는 이벤트가 끝난 뒤의 검출도 성공으로 센다.**
  창이 이벤트 끝을 넘어 걸쳐도 그 창의 참값은 여전히 동결이기 때문이다.
  **기기 입장에서 맞는 숫자는 이벤트 단위다. 동결이 끝난 뒤 울리는 큐는 쓸모가 없다.**
  두 지표를 섞어 쓰면 "윈도우로는 75%가 천장인데 이벤트로는 80%를 요구한다" 같은
  가짜 모순이 생긴다. 모순이 아니라 분모가 다른 것이다 — 6초 이벤트는 윈도우 72%, 이벤트 100%다.
  → `sensitivity_by_duration()` 이 둘을 나란히 찍는다. **보고서에도 나란히 쓴다**

  → **단일 민감도 숫자는 알고리즘이 아니라 데이터셋의 길이 분포를 보고하는 것이 된다.**
  `analysis/evaluate.py :: sensitivity_by_duration()` 이 길이 구간별로 나눠 낸다.
  보고서에는 반드시 나눠서 쓴다 — "민감도 60%"가 **짧은 이벤트가 많아서인지
  알고리즘이 못 잡아서인지**를 그 표 없이는 본인도 설명할 수 없다
- 지연의 표준 정의가 없어(논문마다 기준점이 다르다) 우리 정의를 밝혀 쓴다:
  **라벨이 동결로 바뀐 첫 샘플 → 판정이 처음 참이 된 윈도우의 마지막 샘플**
  (`analysis/freeze_index.py :: latency()`)

**ESP32에서 도는가** — 240 MHz에서 256점 FFT는 약 1~2 ms다. **약 1초마다** 한 번이므로 여유가 크다.

## 4. 소리 출력

수동 부저는 **주파수를 지정해야 소리가 난다**. 능동 부저처럼 전원만 주면 울리는 것이 아니다. 그래서 음높이를 설계할 수 있다.

```
ledcSetup(채널 0, 주파수, 분해능 10비트)
ledcAttachPin(GPIO25, 채널 0)
ledcWriteTone(채널 0, 주파수)   // 주파수를 바꾸면 음높이가 바뀐다
```
- **박자 간격** = `60000 / 케이던스(걸음/분)` ms
- **첫 박만 높게** 낸다. 예: 첫 박 1200 Hz, 나머지 800 Hz. 어디가 한 마디의 시작인지 귀로 구분된다
- **페이드인**: 첫 박은 duty를 0에서 목표치까지 약 100 ms에 걸쳐 올린다. 갑작스러운 소리에 놀라지 않게 하기 위해서다
- 동결이 풀리면(걸음이 다시 검출되면) 즉시 멈춘다

## 5. 상태 기계

```
IDLE      정지 중. 동결 검출 안 함
WALKING   걸음 검출 중. Freeze Index 계속 계산
FREEZE    동결 확정. 부저 구동
RECOVER   걸음 재검출. 부저 정지 → WALKING
```
택트스위치는 어느 상태에서든 **FREEZE로 강제 진입**시킨다. 자동 검출이 놓쳤을 때 사용자가 직접 요청하는 경로다.

## 6. 전력

| 구성 | 소비 |
|---|---|
| ESP32 (WiFi 끔, 80 MHz) | 약 30 mA |
| MPU-6050 | 약 4 mA |
| OLED (평소 꺼 둠) | 0 |
| 부저 (간헐) | 평균 무시 가능 |
| **합계** | **약 35 mA** |

**WiFi를 끄는 것이 전력의 대부분을 결정한다.** 켜면 150~250 mA로 5~8배 뛴다.
이 기기는 실시간 전송이 필요 없으므로, 충전 중에만 WiFi를 켜서 기록을 보낸다.
OLED도 평소 끄고 택트스위치를 누를 때만 켠다.

5000 mAh 보조배터리 기준 이론상 100시간 이상. 실제로는 변환 손실을 감안해도 하루 종일 차고 밤에 충전하는 패턴에 충분하다.

## 7. 착용

- **허리 벨트에 단일 유닛.** 선이 없다
- MPU-6050을 몸통에 밀착 고정한다. 흔들리면 측정축이 돌아가 Freeze Index가 망가진다
- 발목에서 재면 신호는 더 좋지만 착용이 불편하고 유닛이 둘로 늘어난다. 허리를 택한 이유다

## 8. 개발 순서 — PC에서 먼저

**ESP32에서 임계값을 감으로 맞추면 끝이 없다.**

1. **파이썬으로 Freeze Index를 구현한다.** numpy/scipy면 충분하다
2. **동결 구간이 표시된 공개 연구 데이터**로 검증한다. 허리 채널만 뽑아 쓴다
3. 임계값과 유지시간을 데이터로 정한다. 검출률과 오탐률을 같이 본다
4. **검증이 끝난 뒤에** ESP32로 옮긴다. 옮길 때는 알고리즘이 이미 고정돼 있으므로 이식 문제만 남는다
5. 직접 차고 걸으며 기기 동작을 확인한다. 이건 검증이 아니라 **동작 확인**이다

## 9. 단계별 확인 방법

| 단계 | 확인 |
|---|---|
| 1 | 100걸음을 걸었을 때 100에 가깝게 센다 |
| 2 | 걷는 속도를 바꾸면 소리 간격도 따라서 바뀐다 |
| 3 | 정상 보행에서는 울리지 않고, 동결을 흉내 냈을 때만 울린다 |
| 4 | OLED에 그날 횟수가 뜨고, 충전 중 기록이 전송된다 |

## 10. 예상되는 문제

- **중력 성분이 남으면** magnitude가 항상 1 g 근처에 떠 있어 대역 파워가 왜곡된다. 고역통과나 이동평균 차감으로 반드시 제거한다
- **I2C가 불안정하면** 배선 길이를 줄이고 400 kHz에서 100 kHz로 낮춰 본다
- **부저 소리가 작으면** 트랜지스터 구동으로 바꾼다
- **FFT 윈도우가 길면** 반응이 느려지고, 짧으면 주파수 분해능이 떨어진다. 256 샘플은 그 절충점이다
