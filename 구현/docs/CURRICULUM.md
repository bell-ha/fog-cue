# 14주 구현 커리큘럼 — 보행동결 자극 시스템

대상: 코딩은 되지만 임베디드·DSP는 처음인 사람.
전제: `HARDWARE.md`의 핀 배치·센서 설정·신호처리 두 갈래를 그대로 따른다.

```
W1   W2   W3  │ W4   W5  │ W6  │ W7   W8   W9   W10  W11 │ W12 │ W13  W14
└─ 1단계 ─────┘└ 2단계 ──┘ 버퍼  └──────── 3단계 ────────┘ 버퍼  └ 4단계 ┘
   걸음을 센다    멈추면 울린다        동결만 골라낸다            부가 기능
                 ★ 최소 목표          도전 목표
```

**버퍼는 W6과 W12 두 번이다. 반드시 밀리므로 비워 둔다.**
안 밀렸으면 W6은 자기 데이터 수집에 쓴다(W11에서 필요하다). W12는 그냥 쉰다.

---

## 시작 전에 알아둘 것 하나

**64 Hz는 MPU-6050에서 정수 분주로 나오지 않는다.**

DLPF를 켜면 내부 출력이 1 kHz이고 `SMPLRT_DIV`로 나눈다.
`1000 / (1+15) = 62.5 Hz`, `1000 / (1+14) = 66.7 Hz` — 그 사이에 64는 없다.

→ **62.5 Hz를 쓴다.** 대신 **모든 계산을 빈 번호가 아니라 Hz로 한다.**
`bin = round(freq * N / fs)` 로 매번 실제 `fs`에서 뽑으면, DAPHNet(64 Hz)에서 정한 임계값이
기기(62.5 Hz)로 그대로 넘어간다. 빈 번호를 상수로 박아 두면 이 2.3% 차이에서 어긋난다.

W2에서 이걸 모르고 지나가면 W10에서 PC와 기기 값이 안 맞는 이유를 찾느라 며칠을 쓴다.

# 1단계 — 걸음을 센다 (W1~W3)

## W1 · 보드가 살아 있고 I2C에 두 장치가 보인다

**할 일**
1. Arduino IDE에 ESP32 보드 패키지 설치(Espressif). 보드는 `ESP32 Dev Module`
2. Blink 업로드로 경로 확인
3. `Wire.begin(21, 22)` 후 I2C 스캐너 실행
4. MPU `WHO_AM_I`(0x75)를 읽어 `0x68`이 돌아오는지 확인
5. OLED에 글자 한 줄 출력 (U8g2 또는 Adafruit_SSD1306)

**끝났다는 기준**
시리얼에 `0x3C`와 `0x68` 두 주소가 뜨고, OLED에 글자가 보인다.

**막히면 볼 것**
Espressif Arduino 보드 설치 문서 / Arduino `Wire` 레퍼런스 / U8g2 wiki의 생성자 목록

**생길 수 있는 사고**
- **업로드가 `Connecting....___`에서 멈춘다** — BOOT 버튼을 누른 채 업로드를 시작하고, 진행되면 뗀다. USB-시리얼 드라이버(CP2102 / CH340) 미설치도 흔하다
- **스캐너에 아무것도 안 뜬다** — SDA/SCL이 바뀌었거나 GND가 공통이 아니다. 두 모듈 모두 **3V3**에 물린다
- **0x3C 대신 0x3D가 뜬다** — OLED 모듈마다 다르다. 스캐너가 알려준 주소를 쓴다
- **점퍼 접촉 불량.** 전체 14주 중 가장 자주 사람을 괴롭히는 원인이다. 증상이 이상하면 먼저 선부터 다시 꽂는다

## W2 · 정해진 주기로 읽고 파일로 남긴다

**할 일**
1. 레지스터 직접 설정 — `PWR_MGMT_1`(0x6B)=0 으로 sleep 해제 → `ACCEL_CONFIG`(0x1C) ±2 g → `CONFIG`(0x1A) DLPF=4(21 Hz) → `SMPLRT_DIV`(0x19)=15
2. 실제 샘플레이트를 **측정해서** 확인한다(1분간 샘플 수 ÷ 60). 62.5 근처여야 한다
3. FIFO 사용 — `FIFO_EN`(0x23)에 가속도 비트, `USER_CTRL`(0x6A)로 FIFO 활성
4. magnitude = √(ax²+ay²+az²) 계산, 시리얼로 CSV 출력 → PC에서 파일로 저장

**끝났다는 기준**
1분 기록의 샘플 수 오차가 ±1% 이내. **정지 상태에서 magnitude가 1.00 g ± 0.05**.

**막히면 볼 것**
InvenSense MPU-6000/6050 Register Map (PDF) — 레지스터 번호는 전부 여기 있다

**생길 수 있는 사고**
- **sleep 해제를 빼먹는다.** 전원만 넣으면 MPU는 자고 있고 값이 전부 0이다. 가장 흔한 첫 실수다
- **FIFO 오버플로** — FIFO는 1024바이트, 가속도만 쓰면 6바이트/샘플이라 **약 170샘플 ≈ 2.7초**면 찬다. 그보다 자주 비운다. 넘치면 데이터가 어긋나 복구가 안 되므로, 오버플로 비트를 보고 넘쳤으면 **FIFO를 리셋**한다
- **정지인데 magnitude가 1 g가 아니다** — 레인지 설정이 ±2 g가 아니거나(LSB 16384로 나눠야 한다) 축 하나를 빼먹었다

## W3 · 걸음을 센다 → **1단계 완료**

**할 일**
1. **중력 제거** — magnitude에서 이동평균(예: 1초)을 빼거나 0.5 Hz 고역통과
2. 0.5~3 Hz 대역통과(2차 IIR이면 충분)
3. 피크 검출 + **250 ms 불응 구간**
4. 걸음 수 카운트

**끝났다는 기준**
복도에서 **소리 내어 100걸음을 세며 걷고, 기기가 95~105를 센다.** 3회 반복해서 모두 들어온다.

**막히면 볼 것**
scipy `butter`/`filtfilt`로 PC에서 먼저 그려 보고 계수를 옮기면 빠르다

**생길 수 있는 사고**
- **중력을 안 뺐다.** magnitude가 1 g 근처에 떠 있으면 피크 기준선이 흔들려 두 배로 세거나 못 센다. `HARDWARE.md` 10절에도 적힌 1순위 함정이다
- **필터 계수를 64 Hz로 잡았다.** 실제는 62.5 Hz다. 계수를 측정한 `fs`로 계산한다
- **제자리에서 몸만 흔들어도 센다.** 지금은 괜찮다. W5에서 정지 판정이 붙으면 해결된다

# 2단계 — 멈추면 울린다 (W4~W5) ★ 최소 목표

## W4 · 케이던스를 구하고 부저를 울린다

**할 일**
1. 최근 4걸음 간격의 **중앙값** → 케이던스 = `60000 / 간격중앙값(ms)`
2. LEDC로 톤 출력. 박자 간격 = `60000 / 케이던스` ms
3. **첫 박 1200 Hz, 나머지 800 Hz**. 첫 박은 duty를 100 ms에 걸쳐 올린다(페이드인)

**끝났다는 기준**
시리얼의 케이던스가 실제 걸음 속도와 **±5 걸음/분** 안에 들고, 부저가 그 템포로 울린다.

**막히면 볼 것**
ESP32 Arduino core의 LEDC 예제. **코어 버전을 먼저 확인한다**

**생길 수 있는 사고**
- **LEDC API가 코어 버전마다 다르다.** 2.x는 `ledcSetup`+`ledcAttachPin`, 3.x는 `ledcAttach` 하나로 바뀌었다. 예제 코드가 안 컴파일되면 대부분 이 이유다
- **`delay()`로 박자를 만든다.** 그 사이 센서를 못 읽는다. `millis()` 기반 비차단으로 짠다. 이건 나중에 고치기 어려우니 지금 제대로 짠다
- **소리가 작다** — 3.3 V 직결의 한계다. 2N2222 + 베이스 1 kΩ으로 구동하면 커진다

## W5 · 상태기계를 붙인다 → **2단계 완료 · 최소 목표 달성**

**할 일**
1. `IDLE → WALKING → FREEZE → RECOVER` 상태기계
2. **지금은 Freeze Index 없이** 간다 — 걷다가 `STEP_TIMEOUT_MS`(2초) 동안 걸음이 없으면 FREEZE로 본다
3. FREEZE 진입 시 **직전 케이던스**로 박자 시작, 걸음이 다시 검출되면 즉시 정지
4. 택트스위치로 어느 상태에서든 FREEZE 강제 진입

**끝났다는 기준**
걷다가 멈추면 2초 안에 울리고, **다시 걸으면 멈춘다.**
**걷는 속도를 바꾸면 소리 간격도 따라 바뀐다.** → 여기까지가 발표에서 약속한 최소 목표다.

**생길 수 있는 사고**
- **신호등 앞에 서 있어도 울린다.** 지금 구조에서는 당연하다. **이 불편을 직접 겪어 두는 것이 중요하다** — 3단계가 왜 필요한지가 몸으로 남고, 발표 때 "그래서 Freeze Index가 필요했습니다"가 실감나게 나온다
- 상태 전이 조건을 여러 곳에 흩어 놓으면 디버깅이 안 된다. **전이는 한 함수에서만** 일으킨다

밀린 게 있으면 여기서 따라잡는다. 아니라면:

지금 모아 두지 않으면 W11에서 모으러 나가야 하고 그만큼 늦어진다.

# 3단계 — 동결만 골라낸다 (W7~W11) · 도전 목표

**원칙: PC에서 끝내고 옮긴다.** ESP32에서 임계값을 감으로 맞추면 끝이 없다.

## W7 · DAPHNet을 읽는다

**할 일**
1. UCI `Daphnet Freezing of Gait` 데이터셋 다운로드 (CC BY 4.0, 64 Hz)
2. 포맷 파악 — 10열: 시간(ms), 발목 3축, 허벅지 3축, **몸통 3축**, 라벨
3. 라벨: `0` = 실험 구간 밖, `1` = 정상, `2` = 동결
4. **몸통 3축만** 뽑아 magnitude. 단위가 **mg**이므로 1000으로 나눠 g로 바꾼다
5. 피험자별 동결 구간 수와 총 길이, **그리고 구간 길이 분포**를 표로 출력
   ← 길이 분포가 W9에서 필요하다. 짧은 동결이 몇 개인지 지금 세어 두지 않으면, W9의 민감도가 무엇을 분모로 한 값인지 알 수 없게 된다
6. 동결 구간 하나를 matplotlib으로 그려 눈으로 확인

**끝났다는 기준**
피험자별 동결 횟수·총 지속시간 표가 나오고, 동결 구간 그래프에서 **떨림이 눈에 보인다.**

**생길 수 있는 사고**
- **라벨 0 구간을 안 뺐다.** 실험 밖 구간이 섞이면 모든 통계가 틀어진다. 가장 흔한 실수다
- **단위를 안 바꿨다.** mg를 g로 알고 쓰면 모든 값이 1000배다
- **피험자별 편차가 크다.** 동결이 한 번도 없는 사람도 있다. 그런 피험자는 민감도 계산에서 빼고, 오탐 계산에는 쓴다

## W8 · Freeze Index를 구현한다

**할 일**
1. 중력 제거 → 256샘플 윈도우 → Hanning → `numpy.fft.rfft`
   (DAPHNet 64 Hz에서 4.000초, **실기기 62.5 Hz에서는 4.096초.** `HARDWARE.md`의 "정확히 4.0초"는 64 Hz 기준 값이다)
2. **파워는 `|X|²`** 를 쓴다. `|X|`가 아니다
3. `FI = (3~8 Hz 파워 합) ÷ (0.5~3 Hz 파워 합)`
4. hop 64샘플(75% 겹침) → 1초마다 한 값
5. FI 시계열을 라벨과 같은 시간축에 정렬해서 겹쳐 그린다

**끝났다는 기준**
동결 구간에서 FI가 솟는 그림 1장. **정상/동결 FI 히스토그램이 서로 다른 위치에** 있다.

**생길 수 있는 사고**
- **중력을 안 뺐다.** 0 Hz 성분이 0.5~3 Hz 대역으로 새어들어와 분모가 부풀고 FI가 전부 낮게 나온다
- **시간축 정렬 오프셋.** FI 한 값은 4초 구간을 대표한다. 그 값을 윈도우 **끝** 시각에 놓을지 **중심**에 놓을지 정하고 일관되게 쓴다. 검출 지연을 계산할 때 이게 2초 차이를 만든다
- 대역 경계를 빈 번호로 박지 말고 Hz로 계산한다(맨 위 참조)

## W9 · 임계값과 유지시간을 데이터로 정한다

**할 일**
1. 임계값을 넓게 스윕하며 **민감도**와 **시간당 오탐 횟수**를 같이 기록
2. 유지시간 1회 / 2회 / 3회를 비교 (2회가 출발점)
   ★ **유지 회수를 1 올리면 검출이 정확히 1초(= hop) 늦어진다.** 합성 신호 실측 중앙값은
   `1회 2.8초 · 2회 3.8초 · 3회 4.8초`. 오탐이 줄어드는 양과 이 1초를 저울질해 정한다.
   W11에서 오탐을 못 잡아 유지 회수를 올릴 때도 이 대가를 같이 적어 둔다
3. **피험자 단위 교차검증** — 한 명을 빼고 임계값을 정한 뒤 그 사람에게서 성능을 잰다. 모든 피험자에 대해 반복

**끝났다는 기준**
임계값 하나와 유지시간 하나를 **숫자로 확정**하고, 그때의 오탐률과
**이벤트 길이별로 나눈 민감도**를 적어 둔다 (`2~4 / 4~6 / 6~10 / 10초 이상`).
→ 임계값이 `config.h`의 `FI_THRESHOLD`로 들어간다.

**민감도를 한 숫자로 내지 않는다.** 아래 사고 항목에 이유가 있다.

**생길 수 있는 사고**
- **같은 데이터로 정하고 같은 데이터로 평가한다.** 성능이 실제보다 좋게 나온다. 교차검증을 반드시 한다
- **정확도(accuracy)로 보고한다.** 동결은 전체 시간의 소수라 "항상 아니라고 답하기"만 해도 정확도가 90%를 넘는다. **민감도와 오탐을 따로** 본다
- ★★ **단일 민감도 숫자는 알고리즘이 아니라 데이터셋의 길이 분포를 보고하는 것이 된다.** 이게 이 주의 가장 큰 함정이다
  ```
  두 하한이 서로 다른 것의 하한이다
    평가 라벨의 하한  약 2초   4초 창에서 '과반이 동결'이 되려면 2초를 넘어야 한다
                             → 2초 미만은 양성 윈도우가 안 만들어져 분모에서 사라진다
    검출의 하한      약 4초   지연 중앙값 3.8초 (유지 2회)
                             → 2~4초 이벤트는 분모에 있는데 구조상 못 잡는다

  그런데 2~4초만의 문제가 아니다 — 62.5 Hz 실측, 두 지표를 나란히
    길이      윈도우 민감도(W9)   이벤트 검출률(W11)
    2.5초          40%                  0%
    3.0초          48%                  0%
    4.0초          61%                 62%
    5.0초          67%                100%
    6.0초          72%                100%
    12.0초         87%                100%
  ```
  **모든 이벤트가 앞쪽 두 윈도우를 놓친다.** 그 고정 비용이 긴 이벤트에서만 희석될 뿐이라,
  윈도우 민감도는 절벽이 아니라 **길이에 따라 완만히 오르는 기울기**다. 12초짜리도 87%에서 멈춘다.
  ★ **3초 칸을 보라 — 윈도우로는 48%인데 이벤트로는 0%다.** 윈도우 지표는 창이 이벤트 끝을
  넘어 걸쳐도 그 창의 참값을 동결로 치기 때문에, **이미 끝난 동결을 뒤늦게 잡은 것도 성공으로 센다.**
  기기 입장에서 맞는 숫자는 **이벤트 검출률** 쪽이다.
  → **100%를 쫓지 않는다.** 천장이 구조로 정해져 있다. 임계값을 더 내리면 오탐만 는다
  → **길이 구간별로 나눠 보고하고, 제외된 이벤트 수를 같이 적는다.** 그래야 "민감도 60%"가
     *짧은 이벤트가 많아서*인지 *알고리즘이 못 잡아서*인지 본인이 설명할 수 있다
  → 다른 논문의 민감도와 비교하는 것도 **길이 분포가 같을 때만** 의미가 있다

## W10 · ESP32로 옮긴다

**할 일**
1. `arduinoFFT`로 같은 계산을 구현
2. **W8에서 쓴 256샘플 한 구간을 코드에 배열로 박아 넣고**, PC 결과와 FI 값을 비교

**끝났다는 기준**
**같은 입력 256샘플에 대해 PC와 ESP32의 FI가 소수 둘째 자리까지 일치한다.**
이게 맞으면 알고리즘 이식은 끝난 것이고, 남은 건 배선과 타이밍 문제뿐이다.

**생길 수 있는 사고**
- `arduinoFFT`는 **실수부·허수부 두 배열**을 요구한다. 버전마다 API가 다르다(구버전 `arduinoFFT` 객체 vs 신버전 `ArduinoFFT<double>` 템플릿)
- **float vs double.** ESP32는 double 연산이 소프트웨어라 느리지만 256점이면 문제없다. 정밀도 차이로 값이 미세하게 다를 수 있으니 소수 둘째 자리까지만 맞춘다
- **62.5 vs 64 Hz.** 여기서 안 맞으면 대부분 이것이다

## W11 · 기기에서 동결을 잡는다 → **3단계 완료**

**할 일**
1. FI를 상태기계에 연결 — W5의 "2초 멈춤" 조건을 FI 조건으로 교체
2. **W6에서 모은 계단·방향 전환 데이터로 오탐을 확인**
3. 택트스위치 수동 진입 경로가 살아 있는지 확인

**끝났다는 기준** — 셋을 같이 본다
1. **정상 보행 2분 동안 오탐 0회**
2. **6초 이상 지속되는 동결 흉내 10회 중 8회 이상 검출**
   — 세는 규칙: **흉내를 멈춘 시점보다 뒤에 울리면 실패로 센다.** 끝난 뒤 울리는 큐는 쓸모가 없다
3. **기기에서 잰 검출 지연 중앙값이 `PC 실측값 + FIFO 읽기 주기` 안에 든다**
   ← PC 실측값은 **62.5 Hz로 잰 값**을 쓴다. DAPHNet 64 Hz 값과 비교하면 기준선 자체가 다르다
   ```
   hold=1  2.87초      hold=2  3.90초  ← 기본 설정      hold=3  4.92초
   ```
   창 4.096초 + hop 1.024초에서 나오는 값이다. 기기 hop은 1초가 아니라 1.024초다

`6초 이상`이라는 단서가 붙는 이유 — 창이 4초다. 그보다 짧은 흉내는 못 잡는 게 정상이고,
그걸 기준에 넣으면 멀쩡한 구현을 실패로 판정하게 된다.

★ **W9의 민감도와 여기 `10회 중 8회`는 분모가 다르다. 두 숫자를 비교하지 않는다.**
W9은 **윈도우 단위**(참값이 동결인 윈도우 중 몇 개를 맞췄나)라 6초에서 **72%**가 천장이다.
W11은 **이벤트 단위**(한 번이라도 잡았나)라 같은 6초에서 **100%**다 — 지연 3.90초를 넘기니까.
모르고 비교하면 "W9에서 72%였는데 W11이 80%를 요구한다"로 읽혀 멀쩡한 기준을 의심하게 된다.

3번은 진단용이다. 기기 지연은 PC 지연에 **버퍼 대기만** 더해진 값이어야 한다.
이보다 크게 벗어나면 임계값 문제가 아니라 **FIFO를 제때 비우지 않는 버그**이고,
튜닝으로 며칠을 태우기 전에 여기서 걸러진다.

**생길 수 있는 사고**
- **검출 지연 3~4초가 체감상 길다.** 이건 버그가 아니라 구조다. 측정값(`tests/`의 합성 신호):
  ```
  중앙값        hold=1    hold=2    hold=3
  64 Hz(PC)     2.83초    3.83초    4.83초
  62.5 Hz(기기)  2.87초    3.90초    4.92초   ← W11에서 쓸 값
  ```
  4초짜리 창이 동결 구간에 충분히 들어가야 FI가 넘으므로, **유지 조건만 세면 안 되고 창이 채워지는 시간이 더해진다.** `HARDWARE.md` 3절 참조. **줄이려 하지 말고 기록해 둔다.** 선행 연구의 261 ms는 다른 구조에서 나온 값이라 목표로 삼으면 안 된다
- **그래서 '동결 흉내'를 짧게 하면 구조적으로 못 잡는다.** 4초보다 짧은 흉내는 검출 대상이 아니다. 위 통과 기준 2번의 '6초 이상'이 그 이유다
- ★ **이미 끝난 동결을 뒤늦게 잡고 성공으로 센다.** 흉내를 6초 하고 8초쯤 울리면 눈으로는 "잡았다"로 보인다.
  **지연 통계로는 안 드러난다** — 지연은 이벤트 구간 안에서 잡은 것만 세고 밖이면 NaN이라, 늦은 검출은
  큰 값으로 찍히는 게 아니라 **통계에서 통째로 빠진다.** 그래서 기준 2번에 세는 규칙을 박아 둔 것이다
- 오탐이 안 잡히면 임계값을 올리기 전에 **유지시간을 3회로** 먼저 늘려 본다. 임계값을 올리면 진짜 동결도 같이 놓친다.
  단 **대가가 있다 — 유지 3회면 지연이 4.8초**가 되고, 그러면 통과 기준 2번의 `6초 이상`도 빠듯해진다. 올렸으면 지연을 다시 재고 기준도 같이 손본다

# 4단계 — 부가 기능 (W13~W14)

## W13 · 기록과 화면

**할 일**
1. 동결 횟수와 시각을 `Preferences`(NVS)에 저장
2. 버튼을 누르면 OLED를 켜서 **오늘 횟수**를 표시하고 10초 뒤 끈다

**끝났다는 기준**
**전원을 껐다 켜도 횟수가 남아 있다.**

**생길 수 있는 사고**
- **NVS는 쓰기 횟수에 한계가 있다.** 동결이 일어날 때마다 쓰지 말고, 메모리에 모았다가 **일정 주기나 전원 내리기 전에** 한 번 쓴다
- OLED 라이브러리가 RAM을 많이 먹는다. Adafruit이 버거우면 U8g2의 페이지 모드를 쓴다

## W14 · 전송과 마무리

**할 일**
1. **충전 중에만** WiFi를 켜서 기록 전송 (평소엔 꺼 둔다 — 전류가 5~8배 뛴다)
2. 벨트 고정. 유닛이 흔들리면 측정축이 돌아가 FI가 망가진다
3. 데모 영상 — 걷다 멈추면 울리고, 다시 걸으면 멈추는 장면

**끝났다는 기준**
기록이 외부로 전송되고, **벨트에 차고 5분을 걸어도 유닛이 흔들리지 않는다.**

**생길 수 있는 사고**
- **WiFi가 켜져 있으면 ADC2를 못 읽는다.** 심박센서를 붙일 거라면 ADC1(GPIO32~39)에만 붙인다 — `config.h`에 이미 `PIN_PULSE = 34`로 반영돼 있다
- 마지막 주에 케이스를 새로 만들려 하지 않는다. 벨트에 고정만 확실히 한다
