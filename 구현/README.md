# 보행동결 자극 시스템 — 구현

걷다가 발이 굳는 순간에만 박자를 들려주는 허리 벨트.
발표본(`../32203482이종하_개인맞춤형디바이스개발_중간과제.pptx`)의 설계를 코드로 옮긴 것.

```
firmware/    ESP32 펌웨어 (Arduino)
analysis/    PC 검증 코드 (Python) — 임계값은 여기서 먼저 정한다
docs/        커리큘럼
```

## 빌드 단계

`firmware/FoGCue.ino` 맨 위의 `#define STAGE` 로 고른다. 발표 9번의 4단계와 같다.

| STAGE | 하는 일 | 되면 끝 |
|---|---|---|
| 1 | 걸음만 센다 | 100걸음 걸었을 때 100에 가깝게 센다 |
| **2** | **멈추면 울린다** ← **최소 목표** | 멈추면 울리고 걸으면 멎는다 |
| 3 | 동결만 골라낸다 | 정상 보행에선 안 울리고 동결에서만 울린다 |
| 4 | 기록 화면 · 택트스위치 · WiFi | OLED에 횟수가 뜨고 기록이 전송된다 |

**2단계와 3단계의 차이가 이 프로젝트의 전부다.**
2단계는 *멈추면* 울린다. 3단계는 그 멈춤 중에서 *동결만* 골라낸다.
그냥 선 것과 얼어붙은 것은 떨림 주파수가 가른다.

## 결선

```
ESP32 3V3 ──┬── MPU-6050 VCC
            └── OLED VCC
ESP32 GND ──┬── MPU-6050 GND ── OLED GND ── 부저(−) ── 스위치 한쪽
GPIO21 ─────┴── MPU-6050 SDA ── OLED SDA      I2C 공유 (0x68 / 0x3C)
GPIO22 ──────── MPU-6050 SCL ── OLED SCL
GPIO25 ──────── 부저(+)                        수동 부저. PWM으로 주파수를 실어 보낸다
GPIO14 ──────── 스위치                          INPUT_PULLUP, 누르면 LOW
```
자세한 내용은 `../HARDWARE.md`.

## 신호처리 — 한 신호에서 두 갈래

```
MPU-6050 ─ 62.5 Hz ─ magnitude = √(ax²+ay²+az²)
                         │
        ┌────────────────┴────────────────┐
   [A] 걸음 검출                     [B] 동결 검출
   0.5~3 Hz 대역통과                 256샘플(4초) · 75% 겹침
   피크 + 불응 250 ms                Hanning → FFT
   최근 4걸음 간격 중앙값              3~8 Hz 파워 ÷ 0.5~3 Hz 파워
        │                                  │
   케이던스(걸음/분)            FI ≥ 임계 AND 총파워 ≥ 하한 · 2회 연속
        └────────────────┬────────────────┘
                 동결 → 케이던스로 템포 계산 → 부저
```

### 값마다 이유가 있다

| 값 | 왜 |
|---|---|
| **62.5 Hz** | 기기는 64 Hz를 **못 만든다.** MPU는 1 kHz를 정수 분주하는데 62.5와 66.7 사이에 64가 없다. 대역을 Hz로 두고 빈을 fs에서 계산하면 DAPHNet(64 Hz)에서 정한 임계가 그대로 넘어간다 |
| **256샘플** | 기기에서 4.096초, DAPHNet에서 4.000초. 4초는 Bächlin 2010의 선택이다 |
| **75% 겹침** | 약 1초마다 판정. 2회 연속 조건과 합쳐 **검출 지연 3~4초**(측정값) |
| **총파워 하한** | 없으면 서 있을 때 분모가 작아져 FI가 저절로 치솟는다. FI만으로는 '정지'와 '동결'이 구분되지 않는다 |
| **2회 연속** | 계단·방향 전환·물건을 집으려 멈추는 동작은 순간적으로 넘지만 이어지지 않는다 |
| **비율로 본다** | 떨림의 절대 크기는 사람마다·속도마다 다르다. 비율은 덜 흔들린다 |
| **중앙값** | 평균을 쓰면 한 번 튄 간격에 템포가 끌려간다 |
| **DLPF 21 Hz** | 62.5 Hz 샘플링의 나이퀴스트(31.25 Hz) 아래. 44 Hz로 두면 에일리어싱 |

## 먼저 돌려볼 것 — PC와 기기가 같은 값을 내는가

```bash
python3 tests/crosscheck.py
```

`firmware/freeze.cpp`를 **ESP32가 아니라 PC에서 g++로 컴파일해** `analysis/freeze_index.py`와
숫자를 맞춰 본다. 같은 소스 파일이므로, 통과하면 ESP32에서도 같은 값이 나온다.

이게 커리큘럼 **W10의 통과 기준**이다. 여기까지 맞으면 알고리즘 이식은 끝난 것이고
남은 문제는 배선과 타이밍뿐이라, **문제의 범위가 반으로 줄어든다.**

> `analysis/freeze_index.py`의 `_band_power()`와 `firmware/freeze.cpp`의 `bandPower()`는
> **항상 같은 규칙이어야 한다.** 한쪽만 고치면 PC에서 정한 임계가 기기에서 안 맞고,
> 그 원인을 찾는 데 며칠이 든다. 고쳤으면 이 테스트를 다시 돌린다.

## 3단계는 PC에서 먼저

**ESP32에서 임계값을 감으로 맞추면 끝이 없다.**

```bash
cd analysis
pip install numpy
python3 evaluate.py <DAPHNet 폴더>
```

데이터: https://doi.org/10.24432/C56K78 (UCI, **CC BY 4.0**, 64 Hz, 몸통 채널 사용)

평가는 **피험자별 교차검증**으로 한다. 한 사람 데이터로 임계를 정하고 그 사람으로 평가하면
당연히 잘 나온다. **남의 데이터로 정한 임계가 처음 보는 사람에게 통하는지**를 봐야 한다.

나온 값을 `firmware/config.h` 의 `FI_THRESHOLD` 에 넣는다.
`analysis/freeze_index.py` 와 `firmware/freeze.cpp` 는 **같은 값으로 돌아야 한다**.
한쪽만 고치면 PC에서 정한 임계가 기기에서 안 맞는다.

## 안전 관련 — 지우지 말 것

- **첫 박 페이드인** (`FADEIN_MS`) — 갑자기 울리면 놀라서 넘어질 수 있다. 작은 소리에서 시작해 키운다
- **`CUE_MAX_MS` 강제 종료** — 어떤 이유로든 상태가 안 풀려도 멈춘다. **계속 울리는 기기가 되지 않는 것이 이 프로젝트의 전부다**
- **`FI_MIN_POWER`** — 가만히 서 있으면 두 대역이 모두 0에 가까워 비율이 의미를 잃는다. 그건 동결이 아니라 정지다
