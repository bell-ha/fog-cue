# fog-cue — 보행동결 자극 시스템

파킨슨병의 **보행 동결(Freezing of Gait)** 을 감지해, 멈추기 직전 케이던스에 맞춘 리듬을
부저로 들려주는 웨어러블. 평소엔 침묵하고 동결 때만 울려서 리듬 청각 자극(RAS)의
**습관화** 문제를 피하는 것이 설계 의도다.

단국대 개인맞춤형디바이스개발 과제. **발표는 2026-09-27에 끝났고, 지금은 구현 단계(W1)다.**

---

## 지금 상태

| | |
|---|---|
| 단계 | **W1** — 보드가 살아 있고 I2C에 두 장치가 보이는지 확인 중 |
| 막힌 것 | **OLED 핀 헤더가 납땜되어 있지 않다.** MPU-6050도 같을 가능성이 있다 |
| 장비 | 맥 → **LG그램(Windows)** 으로 옮기는 중. USB 케이블은 확보됨 |

코드는 전부 작성돼 있고 검증도 통과한 상태다. 손대야 할 것은 **실기기 브링업**이다.

## 절대 깨면 안 되는 것 세 가지

### 1. PC와 기기가 같은 숫자를 내야 한다

`analysis/freeze_index.py` 의 `_band_power()` 와 `firmware/freeze.cpp` 의 `bandPower()` 는
**글자 그대로 같은 규칙**이어야 한다. 한쪽만 고치면 PC에서 정한 임계값이 기기에서 안 맞고,
그 원인을 찾는 데 며칠이 든다.

규칙은 두 개다:
- `bin = round(Hz × FFT_N ÷ fs)` — **실행 중에** 실제 fs로 계산한다. 빈 번호를 상수로 박지 않는다
- 대역 구간은 `[lo, hi)` **반열림**. 닫힌 구간이면 3 Hz 빈이 분자와 분모에 모두 들어간다

```bash
python3 tests/crosscheck.py     # 둘 중 하나라도 건드렸으면 반드시 돌린다
```

`firmware/freeze.cpp` 를 ESP32가 아니라 **PC에서 g++로 컴파일해** Python과 맞춰 본다.
현재 소수 일곱째 자리까지, 62.5 Hz와 64 Hz 양쪽 모두 일치한다.
(윈도우에서는 g++가 없다. MinGW나 WSL이 필요하다.)

### 2. 기기는 62.5 Hz, DAPHNet은 64 Hz다

일부러 다른 게 아니라 **MPU-6050이 64 Hz를 못 만든다.** DLPF를 켜면 내부 1 kHz를 정수 분주하는데
`1000/16 = 62.5`, `1000/15 = 66.7` 로 그 사이에 64가 없다. DLPF를 끄면 8 kHz base로 64가 되지만
21 Hz 저역통과를 잃어 에일리어싱이 생긴다.

`config.h` 의 `SAMPLE_HZ = 62.5f` 는 **계산값이지 실측값이 아니다.**
MPU는 자이로를 끄면 내부 RC 발진기로 돌아 오차가 ±1% 쯤 된다.
`firmware/bringup/03_mpu_rate` 로 **DATA_RDY 비트가 몇 번 올라오는지** 세서 확인한다
— 루프를 몇 번 돌았는지 세는 건 측정이 아니다. ESP32가 스스로 정한 주기를 다시 읽는 것뿐이다.

잰 값이 1% 넘게 다르면 `SAMPLE_HZ` 를 그 값으로 바꾸고 `crosscheck.py` 를 다시 돌린다.

### 3. 숫자는 출처 원문에 그 숫자가 있어야 한다

이 프로젝트에서 **환자 수를 지어내 한 번 걸렸다.** `120,547명 / 5년간 14% 증가` 는 인용한 원문에
없는 값이었다(실제는 118,504명 · 2021년). 재인용을 거치며 연도와 값이 섞인 것이었다.

숫자를 쓸 때는 원문을 직접 확인한다. 못 찾으면 **"확인 불가"로 남긴다.** 그럴듯한 값을 채우지 않는다.
`docs/DATA.md` 에 검증 실패한 항목들이 이유와 함께 남아 있다.

## 틀린 줄 알고 있어야 할 숫자

발표 자료와 초기 문서에 틀린 값이 들어갔다가 나중에 측정으로 바로잡은 것들이다.
**최종 보고서에 옛 숫자를 재활용하면 안 된다.**

| | 처음 적었던 값 | 맞는 값 |
|---|---|---|
| 검출 지연 | 약 2초 | **3.90초** (62.5 Hz, hold=2 중앙값) |
| 윈도우 4초의 출처 | Freeze Index 원 정의 | **Bächlin 2010**. Moore 2008 원 논문 값은 확인 못 했다 |

"약 2초"는 **유지 조건만 세고 창이 채워지는 시간을 빼먹은** 숫자였다.
교환비는 `유지 +1회 = 지연 + hop 1개(약 1초)` 이고, 실측은 아래와 같다:

```
          hold=1     hold=2     hold=3
64 Hz      2.83초     3.83초     4.83초
62.5 Hz    2.87초     3.90초     4.92초   ← 기기에서 쓸 값
```

## 성능을 보고할 때

**"민감도 X%" 를 한 숫자로 쓰면 안 된다.** 그건 알고리즘이 아니라 **데이터셋의 길이 분포**를
보고하는 것이 된다. 같은 코드가 짧은 동결이 많은 데이터에서는 50%, 긴 데이터에서는 85%를 낸다.

하한이 두 개 있고, **서로 다른 것의 하한**이다:

| | 값 | 무엇의 하한인가 |
|---|---|---|
| 평가 라벨의 하한 | 약 **2.0초** | `(윈도우÷2) ÷ fs`. 이보다 짧으면 참값이 안 생겨 **분모에서 통째로 빠진다** |
| 검출의 하한 | 약 **3.9초** | 창이 채워지고 유지 조건까지 서는 시간 |

**그 사이 2~4초 구간이 함정이다** — 분모에는 들어가는데 구조상 거의 못 잡는다.
그리고 짧은 이벤트만의 문제가 아니다. **모든 이벤트가 앞쪽 두 윈도우를 놓치고**,
그 고정 비용이 긴 이벤트에서만 희석된다. 12초짜리도 87%가 천장이다.

지표도 두 개이고 분모가 다르다:

| 지표 | 세는 것 | 3초 이벤트 |
|---|---|---|
| 윈도우 단위 | 참값이 동결인 윈도우 중 몇 개를 맞췄나 | 48% |
| 이벤트 단위 | 이벤트 구간 **안에서** 한 번이라도 잡았나 | **0%** |

차이의 원인 — **윈도우 단위는 이벤트가 끝난 뒤의 검출도 성공으로 센다.**
창이 이벤트 끝을 넘어 걸쳐도 그 창의 참값은 여전히 동결이기 때문이다.
**기기 입장에서 맞는 숫자는 이벤트 단위다. 동결이 끝난 뒤 울리는 큐는 쓸모가 없다.**

`analysis/evaluate.py` 의 `sensitivity_by_duration()` 이 둘을 나란히 찍는다. 보고서에도 나란히 쓴다.
`event_report()` 는 2초 미만이라 분모에서 빠진 이벤트가 몇 개인지 센다.

## 하드웨어

```
ESP32 3V3 ──┬── MPU VCC ── OLED VCC          MPU-6050  0x68
ESP32 GND ──┼── MPU GND ── OLED GND          OLED      0x3C
GPIO21 ─────┼── MPU SDA ── OLED SDA          (주소가 달라 한 버스를 공유한다)
GPIO22 ─────┴── MPU SCL ── OLED SCL
GPIO25 ──────── 수동부저(+)                   부저(−) → GND
GPIO14 ──────── 택트스위치                    반대쪽 → GND, INPUT_PULLUP
```

- **3V3에 꽂는다. VIN(5V) 아니다.** ESP32의 신호가 3.3V다
- **MPU의 `AD0`는 비워 둔다.** 3.3V에 닿으면 주소가 `0x69`로 바뀐다
- **수동부저다(KIT 07번).** 능동부저(06번)는 정해진 한 음만 내서 못 쓴다
- ESP32 코어 **2.0.17** 기준. LEDC API가 3.x에서 바뀌었으니 버전을 먼저 확인할 것
  (2.x는 `ledcSetup`+`ledcAttachPin`, 3.x는 `ledcAttach`)
- 심박센서(PPG)는 이 프로젝트에서 안 쓴다. 붙인다면 **ADC1(GPIO32~39)에만** —
  WiFi가 켜져 있으면 ADC2를 못 읽는다
- 아두이노 우노는 **안 쓴다.** Freeze Index 하나에 RAM 4 KB가 필요한데 우노는 전체가 2 KB다

## 구조

```
firmware/        ESP32. 여기만 기기에 올라간다
  config.h         모든 상수. 코드 본문에 숫자를 쓰지 않는다
  gait.*           걸음 검출 + 케이던스 (중앙값. 평균이 아니다)
  freeze.*         Freeze Index. analysis/freeze_index.py 와 짝이다
  cue.*            부저. LEDC PWM
  FoGCue.ino       메인. #define STAGE 로 단계를 고른다
  bringup/         단계별 확인 스케치. 01 → 02 → 03 순서로 통과시킨다
analysis/        PC. 임계값을 여기서 정한다
tests/           crosscheck.py — PC↔기기 값 일치 검사
docs/            CURRICULUM.md(14주) · HARDWARE.md · DATA.md(출처 검증)
```

`FoGCue.ino` 의 `STAGE` 가 발표의 4단계와 대응한다. **W5(STAGE 2)까지가 발표에서 약속한 최소 목표**이고,
그 뒤는 전부 더하기다. 2단계는 Freeze Index 없이 `STEP_TIMEOUT_MS` 만으로 돌게 해서
3단계가 밀려도 같이 무너지지 않게 분리해 뒀다.

## 작업 방식

- **바꾼 상수는 `config.h` 에만 둔다.** 코드 본문에 숫자를 쓰지 않는다
- **측정한 CSV는 원본을 지우지 않는다.** `data/raw/YYYYMMDD_상황.csv`
- 2시간 넘게 같은 자리에 막히면 적어 두고 다음 항목으로 넘어간다
- 주가 끝나면 커밋한다. 메시지에 그 주의 **"끝났다는 기준"** 통과 여부를 쓴다

### 말투

**공대 문서다. 비유나 순우리말 조어를 쓰지 않는다.**
이 프로젝트에서 이름을 「아타카」, 「걸음박자 벨트」로 두 번 제안했다가 모두 거부당했다.
원인은 *이름 짓기*를 반복한 것이고, 필요했던 건 *기능 명시*였다.

### 자주 나온 실패 유형

- **문서 하나는 맞는데 두 문서가 서로 모순된다.** 64 Hz vs 100 Hz, 지연 2초 vs 3.9초가 그렇게 나왔다.
  고칠 때 그 숫자가 **다른 파일에도 있는지** 전부 grep한다
- **두 숫자가 결론이 같으면 근거도 같다고 읽는다.** 2초와 6초는 세 배 차이인데 둘 다
  "짧은 동결은 못 센다"로 끝나서 한 묶음으로 읽었다가 그 사이 구간을 지워버렸다.
  **결론이 같을 때 근거가 같은지 따로 확인한다**
- **확인 안 한 것을 단언한다.** 사진을 "대략" 보고 `추가 구매 0개` 라고 문서에 적었는데,
  나중에 제대로 보니 OLED 핀이 납땜돼 있지 않았다
- **표가 산문보다 거짓말을 못 한다.** 두 값이 한 칸에 들어가려 하거나 칸이 비면 거기가 문제 지점이다
